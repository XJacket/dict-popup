# 02 — 取词失败：剪贴板序号变化但读不到文本

- **Type:** bug
- **Status:** ready-for-agent
- **Reported:** 2026-10-25（用户实机反馈，Windows 11 记事本）
- **Area:** dict-input / capture

## 诊断进展（2026-10-25 下午）

已建起确定性反馈回路 `dict-input/tests/clipboard_loop.rs`：测试自己创建窗口 +
`EDIT` 控件、`SetFocus`、`EM_SETSEL` 选中文字，然后**在进程内**跑生产取词代码，
主线程负责泵消息。1 秒内可复现/验证。

结论：

- 当取词进程**自己拥有前台焦点控件**时，`SendInput` + 剪贴板读取**工作正常**
  （0.66 s 取回 "apple"），说明取词实现本身没有根本性错误；
- 失败时"剪贴板序号变化"曾经是**假信号**：我们自己的"还原剪贴板"也会让序号 +1，
  而旧代码在还原**之后**才采样序号。已改为在还原**之前**采样；
- 新增兜底：注入没有到达目标时，直接给前台线程的焦点控件发 `WM_COPY`
  （记事本等标准编辑控件认这条消息，不需要合成输入）；
- 失败信息现在区分「注入未到达目标窗口」与「到达了但读不到文本」，并附带读取失败原因。

## 现象（用户原文）

```
取词失败：剪贴板未更新：前台窗口 class='Notepad' hwnd=0x181742；
剪贴板序号 817→822（剪贴板变了但没有文本）；
UI Automation：取词失败：未找到可读取的文本控件（扫描 0 个元素）
```

## 已验证

- 前台窗口确实是 Notepad（不是我们的卡片，也不是 DSH 窗口）；
- **剪贴板序号变化了 5 次**，说明 `Ctrl+C` 已经被记事本处理，剪贴板被写过；
- 但我们的 `read_text()` 没读到 `CF_UNICODETEXT`；
- 剪贴板读/写本身是好的：`examples/clipboard_probe.rs` 往返成功；
- 我们进程的 `SendInput` 能改变剪贴板（把前台切到浏览器时序号 762→767）；
- UIA 路径在我们的 COM 客户端里只能看到 1 个空 Pane（STA/MTA、
  `CoInitializeSecurity`、桌面根搜索都试过；托管 UIAutomationClient 能看到完整树，
  说明是我们的条件构造问题），因此 UIA 目前不可依赖。

## 待确认（需要报告者回答）

1. 出现这条错误的**同一时刻**，在记事本里按 `Ctrl+V` 粘贴，粘出来的是什么？
   - 有内容 → 复制成功，是我们读取有问题（查 `read_text` / 剪贴板所有权）
   - 粘贴无变化 → 记事本并没有真的复制（选区已丢失）
2. 选中的是**鼠标拖选的文字**，还是 `Ctrl+A` 全选？
3. 按下热键前后，鼠标有没有点击过别的地方（点击会清掉选区）？

## 假设排序

1. **选区在按下热键时已不存在**（点击了别处 / 卡片抢焦点），记事本执行了一次
   "空复制"：剪贴板被清空或写入非文本内容 → 序号变、无文本。最符合"变了 5 次"。
2. 记事本把内容以 **延迟渲染** 提供，我们在 owner 未就绪时 `OpenClipboard`
   或 `GetClipboardData` 失败（当前重试 8×12 ms，可能不够）。
3. 剪贴板里是 **CF_TEXT 而非 CF_UNICODETEXT**（记事本不该如此，但不排除）。

## 修复方向（等信息确认后择一）

- 若属假设 1：热键触发时若检测到"无选区"，返回明确的"没有选中文字"而不是
  现在的"剪贴板未更新"；同时把卡片显示时机再往后挪，避免抢焦点。
- 若属假设 2：把读取重试提高到 ~600 ms，并接受 `CF_TEXT`（ANSI）作为回退。
- 若属假设 3：读取时按 `CF_UNICODETEXT` → `CF_TEXT` 顺序尝试。

## 验收标准

1. 记事本里鼠标选中英文单词 → 按热键 → 卡片显示释义；
2. 未选中任何文字时，提示"没有选中文字"且**不修改**用户剪贴板；
3. 失败信息包含前台窗口类名与剪贴板序号（已有）。

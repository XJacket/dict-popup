# ADR-0001: 用 UIAccess 解决跨完整性级别的取词拦截

- **状态**：已接受（2026-10-25，已实机验证）
- **范围**：`dict-input` 取词路径、构建与发行方式

## 背景

取词依赖合成 `Ctrl+C` 后读剪贴板。Windows 的 UIPI 规则是：**调用方完整性级别低于目标窗口时，
合成输入被静默丢弃**——`SendInput` 返回成功，但目标程序收不到任何按键。

实际表现：

- 程序以普通权限启动、目标是以管理员身份运行的程序 → 取词必定失败；
- 更早的一次误判：exe 放在带 Low 完整性标签的目录里，进程被降级，连普通记事本都取不到词。

签名本身**不**参与这条判断——它只解决“发布者是谁”。

## 决定

采用 **UIAccess**：manifest 声明 `uiAccess="true"`，二进制用受信任证书签名，
并安装到 `%ProgramFiles%`。满足三项后系统授予进程 UIAccess，令牌被提升到 High 完整性级别，
从而可以跨完整性级别读取 UI 与注入输入。

## 依据（实测）

自签证书 + `%ProgramFiles%` 安装、**非提权**启动，令牌为：

```text
elevated=False  uiaccess=True  integrityRid=0x3000 (High)
```

并在**以管理员身份运行**的记事本里成功取词。未签名时同 manifest 的 exe **完全无法启动**
（`ERROR_ELEVATION_REQUIRED`, 740）。

## 影响

- **构建**：`build.bat /uiaccess` 产出带 UIAccess manifest 的变体；默认产物不带
  （未签名时带它会导致程序无法启动）。
- **发行**：UIAccess 变体必须在签名之后才可用；正式签名走 SignPath Foundation。
- **安装**：需要一次管理员安装（复制到 `%ProgramFiles%`、创建开始菜单快捷方式），
  之后以普通权限启动即可。
- **安全边界**：UIAccess 允许驱动其他程序的 UI，属高权限；不在安全桌面（UAC 提示、锁屏）生效。
- **自检**：程序启动时记录 `privilege: uiaccess=… elevated=… integrity=…`，
  设置页显示一行状态，`diagnostics` 报告同样包含这三项。

## 备选方案与放弃原因

| 方案 | 放弃原因 |
|---|---|
| 每次以管理员运行 | 每次 UAC 提示；不是可发行产品的默认体验 |
| 常驻提权 helper 进程 | 为一个取词功能长期维持高权限组件，攻击面不划算 |
| 只签名、不加 UIAccess | 签名不改变完整性级别，跨 IL 仍然失败（本次已证实） |
| 只用 UIA 读取，不注入 | UIA 同样受 UIPI 限制；低 IL 读不到高 IL 窗口 |
| 剪贴板监听（用户自己复制） | 零权限可用，但牺牲“选中即译”；保留为未来的降级路径，不作为首选 |

## 后果

未来若有人提议“只要签名就能解决取词”，不必重新讨论——本 ADR 与实测数据已经否定了它。
若 SignPath 申请失败，退回自签 + 企业分发受限的发布方式，或重新考虑“复制即翻译”模式。
